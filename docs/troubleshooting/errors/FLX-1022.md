# FLX-1022

## The rule

A committed processor is reused only when the compile request it was generated from is unchanged; otherwise it must be regenerated by a signed-in build.

## Why the compiler says this

The build digests the compile request it would send, which covers everything generation reads from your nodes, and compares it with the digest stamped beside the committed processor. The committed processor cannot be reused (something generation reads has changed since the processor was generated), so it may not describe this graph. Compiling it anyway is how a node edit builds cleanly and then fails at run time. Regenerating needs the compiler, and this build has no managed compiler credential, so it stops here, before sending anything.

## How to fix it

Sign in (`./mvnw fluxtion:login`, or set FLUXTION_API_TOKEN in CI) and rebuild: the processor is regenerated and restamped, and later builds reuse it. In an authoring project, run `./generate.sh` instead.

## Which builds raise it

**A build in ensure mode** (the Maven plugin's `ensureProcessor`), and only when the committed processor cannot be reused and the build has no managed compiler credential. It is raised before anything is sent. A build that is signed in regenerates instead, and a build whose compile request is unchanged reuses the committed processor without signing in.
