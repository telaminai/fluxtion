# FLX-1031

> the cpp target cannot carry node state — node 'spreadModel' field 'tickSizes' is a java.util.Map

| | |
|---|---|
| **Severity** | ERROR |
| **Category** | TARGET |
| **Element** | `FIELD` |

## The rule

Configured node state is carried into generated source, or refused by name.

## Why the compiler says this

Fluxtion reproduces each node in generated source WITH the state you configured, so a graph built with a field set to 64 generates a processor holding 64. The Java target serialises this field; the cpp target has no representation for it. Emitting the node without the field would produce two builds of one graph that compute different things, differing silently and detectable only by comparing audit logs at runtime — so it is refused instead. Some types are refused deliberately rather than for want of effort: a Map could be a hash map, a sorted vector, a perfect hash or a flat array, and choosing would be the compiler picking a hot-path representation on your behalf.

## How to fix it

If this is not configured state, say so: mark the field transient or @FluxtionIgnore and build it in @Initialise — both are honoured before this check. If it IS configured state, register a field serialiser for the cpp target and it is offered the field before this refusal. Serialisers run where the node OBJECT is — on the machine that BUILDS the graph — so for a remote build they belong on your classpath, not the generator's. A graph that generates locally and refuses remotely is usually this and nothing else.

## Which builds raise it

**The target named in the message, on source-generating (AOT) builds only.** These are capability refusals, not modelling errors: the same graph generates for other targets, and an interpreted or in-process build never renders a target at all. Expect to meet one for the first time when you add a second target to a graph that has always built — that is the refusal doing its job, because the alternative is a processor that silently computes something different from its twin.

## Reading it programmatically

This diagnostic is also written to the machine-readable report — the opt-in sidecar (`-Dfluxtion.diagnostics.sidecar=true`), or `FluxtionDiagnostics.capture(...)` for a caller that wants the objects:

```json
{
  "code": "FLX-1031",
  "severity": "ERROR",
  "category": "TARGET",
  "element": { "kind": "FIELD", … }

```

Select findings by `severity`, never by position: a failing build's report also contains any warnings it found, and `diagnostics[0]` is not the cause of the failure.
